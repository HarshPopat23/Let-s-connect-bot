# I know nothing about open source. Where should I begin

Learn basic Git and GitHub, choose a project you actually use or care about, read its contributor guide, run it locally and observe its public communication. Start with a verified, useful task that matches your current skills. Documentation, testing, reproduction, design, translation and community support are valid contributions.

# Should I learn the entire codebase first

No. Understand the project's purpose and architecture at a high level, then use one issue as a path through the relevant subsystem. Reproduce the problem, trace the related code and expand your understanding gradually.

# How many pull requests should I make daily

There is no useful daily target. Contribution quality, relevance, testing, review behavior and sustained participation matter more than count. A difficult pull request may take weeks.

# Can I use AI to solve issues

Use AI to learn, locate code, explore alternatives and generate candidate tests. Submit only work you have independently verified and can explain. Follow the project's AI policy. Never use AI to create repository spam or to pretend you performed work you did not understand.

# Should I direct-message a maintainer

Use public project channels unless the project asks for direct contact or the matter involves safety, privacy or security. Public discussion preserves knowledge and avoids placing repeated support work on one person.

# My pull request has no review. What should I do

Check the contribution guide and usual response time. Confirm tests pass and the pull request is focused. Wait a reasonable period, then post one polite follow-up with a short status and any deadline. Meanwhile, review related work, improve tests or contribute elsewhere.

# Do merged pull requests guarantee GSoC or LFX selection

No. They can demonstrate familiarity and follow-through, but programs also consider project fit, proposal quality, communication, available slots, eligibility, technical judgment and mentor capacity. Organizations make their own selections.

# Which technology has the lowest competition

Choosing only for low competition is fragile. Choose a project whose purpose interests you and whose stack you can realistically learn. Selection programs change each cycle, while genuine project knowledge remains useful.

# Can I contribute without coding

Yes. Valuable work includes documentation, tests, issue reproduction, accessibility, design, localization, tutorials, release work, community support, event organization, research, security review and code review when you have enough context.
