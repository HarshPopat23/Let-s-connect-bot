# Search before opening

Search open and closed issues, pull requests, discussions, release notes and documentation. Different words may describe the same problem. A closed issue can explain why an idea was rejected or how behavior changed.

# Write a reproducible bug report

State the affected version, operating system, installation method and relevant configuration. Provide the smallest reproduction, exact expected behavior, actual behavior, logs and whether it previously worked. Remove secrets and personal data.

Do not paste a vague AI-generated description. If you cannot reproduce the problem, clearly label the report as an observation and explain the missing information.

# Propose a feature with purpose

Describe the user problem before the solution. Explain who benefits, current workarounds, scope, compatibility risks and alternatives. Large features may require a design proposal, enhancement document or community discussion before code.

Avoid presenting generated code as proof that a feature is easy. Review, tests, documentation, long-term maintenance and backward compatibility often cost more than the first implementation.

# Ask to work on an issue

Read the repository assignment policy. If assignment is required, comment with evidence that you understand the problem and a short approach. Do not post only "assign me" when the template requests more detail.

If someone is assigned, do not race them with a duplicate pull request. Ask whether help is useful or choose another issue. If an assignment is inactive beyond the project's stated period, let a maintainer decide reassignment.

# Scope changes

If investigation shows that the issue is larger, pause and explain the new scope before making a broad change. Split independent work into separate issues or pull requests when reviewers request it.

# Security exception

Do not open a public issue for a suspected vulnerability until you read SECURITY.md. Use private vulnerability reporting or the listed security contact.
