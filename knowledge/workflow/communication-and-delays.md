# Ask questions that are easy to answer

Include the repository and issue link, exact problem, relevant version, what you read, what you tried and the smallest remaining question. Use code blocks or logs only when needed and remove secrets.

Ask in the project's preferred public channel. Keep one topic in one thread. Do not cross-post the same question to an issue, discussion, Slack and several direct messages at once.

# Respect maintainer time

Many maintainers are volunteers or balance project work with employment. Lack of an immediate reply is not rejection. Check contribution documentation for service expectations and observe how quickly similar work is reviewed.

Avoid tagging multiple people. Choose the component owner or reviewer indicated by CODEOWNERS, labels, recent history or project guidance.

# Follow up professionally

After a reasonable wait, send one concise follow-up. For example: This is ready for review, all documented tests pass and I addressed the earlier scope question. Is there any missing information, or should I seek another component reviewer?

Do not post daily reminders, guilt messages or claims that an application deadline obligates maintainers to review. Your personal program deadline does not automatically become a project priority.

# Use waiting time well

Review your diff, add edge-case tests, improve the description, update documentation, test another contributor's related pull request, answer newcomer questions or choose an independent task. Avoid stacking unreviewed large changes that depend on one unresolved design.

# Escalate only through documented paths

For conduct concerns, use the code of conduct reporting contact. For vulnerabilities, use private security reporting. For governance decisions, use the project's escalation process. Do not convert disagreement into public harassment.
