# Ways to contribute

Kubernetes contributions include features, bug fixes, design, documentation, blogs, localization, testing, release work, contributor support and community participation. Start at the Kubernetes contributor site and identify the Special Interest Group or Working Group responsible for your area.

# Join the workflow

Read the Kubernetes community contributor guide, code of conduct and repository-specific instructions. Join Kubernetes Slack through the official community path and use the relevant SIG channel. Attend newcomer and SIG meetings; agendas and recordings often provide essential context.

Kubernetes automation uses commands, labels, owners files, tests and contributor roles. Do not copy commands from unrelated repositories. Follow the instructions in the pull request template and bot messages.

# Contributor License Agreement

Kubernetes contributions may require the CNCF Contributor License Agreement. Your Git commit name and email must match the identity used for the agreement. If the CLA check fails, follow the official troubleshooting guidance rather than repeatedly changing code.

# Membership is earned responsibility

Anyone can begin contributing, but organization membership and higher roles have documented requirements and sponsorship. Membership is not the same as appearing in commit history.

As of the source update, member requirements include two-factor authentication, current affiliation information, multiple contributions showing continuing commitment, at least one meaningful merged pull request, active participation in a subproject, reading the contributor guide, subscribing to the developer mailing list and sponsorship by two qualified reviewers from different member companies. Contributions may include authorship, review, issues and community discussion. Applicants open the documented membership request and obtain sponsor confirmations.

Reviewer and approver are separate, scoped roles with further experience requirements. A reviewer entry belongs to a specific OWNERS area, and acceptance also requires an approver. Rules can change, so use the current Kubernetes community membership document rather than an informal pull request count.

# Review expectations

Large Kubernetes changes often require issue, design and SIG agreement before implementation. Keep changes focused, run required tests and respond carefully to automated and human review. Maintainer availability may create delays.
