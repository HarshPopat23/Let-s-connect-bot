# Start with purpose and fit

Prefer software you use, a problem domain you care about or a technology you want to understand deeply. Read the website and README until you can explain who uses the project, what problem it solves and why the proposed issue matters.

Match the project to your present abilities and learning capacity. You do not need to know the full stack, but you should be able to set up the development environment and learn the relevant subsystem without depending entirely on AI.

# Evaluate project health

Inspect recent commits, releases, issue responses, pull request reviews and community meetings. Activity should be judged across several weeks or months because volunteer projects can be quiet temporarily.

Healthy newcomer signals include a current contributor guide, a code of conduct, reproducible setup, labeled starter issues, respectful review, multiple active maintainers and public decision-making. Warning signals include many abandoned pull requests without explanation, broken setup, hostile communication, unclear licensing, expired community links and no response across all channels.

Do not choose by star count alone. A smaller project can provide better context and mentorship. A large project can offer strong processes but require more patience.

# Compare candidate projects

Score each candidate from one to five on genuine interest, setup success, issue clarity, maintainer responsiveness, documentation quality, skill fit and available weekly time. Select one primary project and optionally one backup. Avoid spreading early effort across many unrelated repositories.

Before committing months for a mentorship program, review previous program projects and current organizational priorities, but never assume an organization will return or offer the same project. Official program listings for the current cycle are authoritative.

# Find useful work

Search good first issue, help wanted, documentation, testing and component labels. Read accepted and rejected pull requests to learn project standards. Attend a meeting and listen before proposing major changes.

User-reported bugs, setup friction, missing tests and unclear documentation can be highly useful. Confirm that the maintainers want the work, especially for old issues or major refactors.
